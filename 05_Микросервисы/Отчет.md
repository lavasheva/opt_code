# Практическое задание 3 Рефакторинг микросервисов
Вариант 6. Дополнительный сервис способов оплаты. Стек исходника сохранён: Node.js, Express, API Gateway. Добавлены PostgreSQL, Sequelize, миграция и Redis.

## Структура и ответственность
Модуль | Назначение
--- | ---
api_gateway | Маршрутизация, Circuit Breaker, агрегация, кэш
service_users | CRUD пользователей и Sequelize-модель
service_orders | CRUD заказов и фильтр userId
service_payment_methods | CRUD способов оплаты и проверка пользователя
service_users/migrate.js | Инициализация таблиц в транзакции и журнал миграций
PostgreSQL | Постоянное хранение, последовательности id, FK
Redis | Краткоживущий кэш индивидуальных GET

В исходнике данные находились в объектах fakeUsersDb и fakeOrdersDb и исчезали после остановки. Теперь данные живут в PostgreSQL и Docker volume. Для users/orders произвольные исходные поля сохранены в JSONB; id выдаётся БД. Изменение id через тело запроса запрещено, чтобы адрес ресурса и первичный ключ не расходились. Для корректных исходных запросов формы успешных ответов сохранены. Пользовательский PUT объединяет поля, а PUT заказа заменяет их, как в исходнике. Обход фильтрации выполнен в БД.

## Схема хранения
users: id integer primary key, data jsonb. orders: id integer primary key, data jsonb. payment_methods: id, userId, type, lastFour, expiresAt. payment_methods.userId ссылается на users.id с ON DELETE CASCADE; есть индекс userId. Связь orders.data.userId с users логическая: исходный CRUD не проверял существование пользователя для заказа, поэтому новый FK не вводится молча.

Миграция 001_initial создаёт таблицы через Sequelize QueryInterface в транзакции и заносит запись в migrations. Compose запускает её перед сервисами; повторный запуск не пересоздаёт таблицы. Модель не вызывает sync(force:true).

## Сервис способов оплаты
Метод и путь | Назначение
--- | ---
POST /payment-methods | Создать способ оплаты, HTTP 201
GET /payment-methods?userId=1 | Список, при необходимости по пользователю
GET /payment-methods/:id | Чтение одного, 404 при отсутствии
PUT /payment-methods/:id | Частичное обновление
DELETE /payment-methods/:id | Удаление

Пример тела: {"userId":1,"type":"card","lastFour":"1234","expiresAt":"2099-12"}. Разрешены типы card и bank_account, последние четыре цифры - ровно четыре цифры, срок - YYYY-MM, не истёкший на конец месяца UTC. userId должен быть положительным целым. Неизвестные поля отклоняются: полный номер карты и CVV сервису не нужны. Перед сохранением выполняется HTTP-проверка пользователя с таймаутом, а FK защищает от удаления пользователя между проверкой и INSERT. Валидация отделена в validation.js и проверяется без БД.

## Шлюз и устойчивость
Для каждого сервиса существует отдельный Circuit Breaker opossum. Таймаут HTTP 2 с, breaker 3 с, порог ошибок 50%, минимум три запроса, повторная проба через 5 с. Ожидаемые HTTP 4xx передаются клиенту и не считаются авариями сервиса. Ошибки соединения и 5xx влияют на breaker. При недоступности ответ 503; успешная запись не имитируется.

GET /users/:id/details параллельно получает пользователя и заказы через Promise.all. Ошибка пользователя или заказов не превращается в пустой успешный ответ. Фильтрация заказов передаётся сервису, а не выполняется после выгрузки всех заказов. /health показывает состояния breaker; /status сохраняет исходный ответ. Служебные пути orders/status и orders/health не перекрываются параметром id.

## Кэш
Кэшируются успешные индивидуальные GET /users/:id, /orders/:id и /payment-methods/:id, TTL 30 секунд. Для демонстрации заголовок X-Cache принимает HIT или MISS. Списки и агрегация не кэшируются: меньше зависимостей инвалидирования.

После POST, PUT или DELETE версия кэша соответствующего сервиса увеличивается в Redis. Старые ключи больше не читаются и истекают по TTL. Это защищает от случая, когда медленное чтение записало старое значение уже после изменения данных: оно запишется под старой версией. При удалении пользователя меняется и версия способов оплаты из-за каскадного удаления. При недоступности Redis запрос обслуживается без кэша; полный контроль согласованности при сетевом сбое Redis потребовал бы отдельного механизма, здесь допустима ограниченная TTL устарелость.
